# 项目需求看板

- 状态：用户于 2026-10-20 确认设计并要求分阶段在隔离 bench 截图验收。
- 适用：产品开发、软件开发。
- 扩展 2026-10-16-bot-handoffs.md 中“不做看板任务对象”的旧边界。消息派活树继续保留；需求是独立的持久对象，不把回合结束等同需求完成。

## 已确认的产品规则

项目使用 DSH 已注册 workspace；需求保存 workspace id 与路径快照。项目切换条只切看板，不修改 Bot 全局工作目录或停止工作。复用 DS Bot 主导航、主题、头像、表单和实时更新机制。

外层四列：待开始、进行中、需要你、已完成。需求确认、需求澄清、方案设计、代码实现、代码验证是卡片内部阶段。「需要你」由未解决的决策生成，不覆盖阶段，也不自动暂停独立且已授权的步骤。

一张需求有一位主负责人、多位协作者，每个步骤只有一位负责人。主负责人协调、汇总问题和结果；协作者更新自己的步骤。Bot 可跨项目参与，但每项需求保有独立工作上下文和目录。多人需求首次开始时建立关联群，恢复和返工复用；单人需求使用任务对话。

用户确认内容和负责人后点击开始。保存待开始需求不派活。方案设计完成后需用户确认，才能开始实现。验证通过进入最终验收，只有用户可以确认完成。重要产品范围、体验、验收标准取舍需要用户；实现细节和已授权范围内的修复由 Bot 自主执行。

每个 Bot 同时执行一项看板工作，其他工作显示在队列里；同项目同时只有一张需求占用实现及验证阶段。不同 Bot 分工需明确修改范围。合并、发布、生产重启只有明确纳入需求范围才执行。

运行中修改目标、范围或验收标准形成新修订，说明影响并重新确认受影响方案；普通笔误直接保存。提交验收逐条对应标准、产物和验证结果，区分失败、未执行和环境限制。多人需求优先由非实现者审查，单人自验标明未独立复核。

暂停停止新派发并请求执行者停止；取消保留产物和记录。重启先核对事实再恢复，不能把断线当完成，也不能重复派发。决策、验收、失败和重要阻塞提醒用户，普通进度只更新看板。主导航和项目条展示待处理数量。

## 分阶段验收

1. 看板与待开始需求：真实插件主导航、项目切换、四列卡片、桌面详情抽屉和手机全屏详情；待开始需求创建/编辑/持久化；明确标注 bench 中的场景为合成演示数据。执行与审批按钮在下一阶段接入，不使用假按钮宣称已派发。
2. 需求工作流：Bot 工具权限、步骤、阶段交付、用户决策版本、关联任务对话和群、验收及退回。用户决定与 Bot 回合分开记录。
3. 调度和恢复：Bot 队列、项目实现锁、派发幂等、暂停/取消、重启恢复、重要通知；对竞态和故障进行专门验证。

每阶段在独立功能分支及新 DSH_HOME 使用 mock 模型验证并提供截图。生产 profile、Caddy 和服务不作为测试环境。用户验收前不部署到生产。

## 第一阶段数据与接口

沿用团队 state.json 的单写者锁、排队写入和 revision，新增 board version 1、nextNumber、cards。卡片包含项目、负责人、范围与验收标准、版本、流程状态、阶段、步骤、决策、产物和活动。

- board-view：仅使用 workspaceRegistry.list() 的公开 API 发现项目，返回项目待处理数和卡片。
- board-create：只创建待开始需求，不接收客户端指定状态；requestId 避免重试重复创建。
- board-edit：只允许编辑待开始需求；version 防止旧窗口覆盖新值。

Web 沿用当前前台 1.5 秒、后台 10 秒拉取策略。接口错误保留已有界面并展示错误；异步旧响应不能覆盖新版。重启读回持久卡片。Bot 工具与用户接口共用同一领域服务。

## 第二阶段：真实需求工作流

用户接口增加 board-start、board-decide、board-retry。开始时检查描述、标准、成员和注册项目路径；只派发主负责人做澄清与方案。决策绑定 scopeVersion、planVersion、decisionVersion；旧页面不能批准已被退回或替换的方案。需求状态、步骤、决策和活动先写入，再发送 DSH 消息。

多人需求复用群聊模块，每人有独立成员 Session，固定到该需求项目。单人需求使用同一会话基础设施的单成员任务对话，用户从卡片直接打开。绑定到看板的任务会话不可通过普通群设置改成员、主负责人、目录或权限；不会提升普通 Bot 为 Main Bot。

工具：read_project_board、create_requirement、plan_requirement、update_requirement_step、resume_requirement_step、ask_requirement_user、submit_requirement。Bot 创建的需求仍为待开始。变更只能从该需求的成员会话发起；只有主负责人可以提交方案、问用户、恢复受阻步骤、提交验收。协作者只能更新自己的已派发步骤。

方案包含步骤 id、唯一执行者、实现/验证阶段、明确修改或审查范围、依赖。拒绝循环依赖与非成员指派；多人方案必须包含未参与实现的验证者。用户批准后自动派发依赖已满足的步骤，同 Bot 的步骤依次推进；所有实现步骤完成才开始验证。验证完成后唤回主负责人汇总，不把回合结束当业务完成。

审批前与未被派发的成员只能使用只读调查及看板工具；不能绕过看板私信派活或改全局 Bot 设置。项目目录消失时报错，不回落到团队默认目录。同项目已有需求实现或验证时，其他方案的批准被拒绝，保留待确认；自动排队批准属于第三阶段。

交付必须包含所有验收标准的有序证据（passed/failed/not-run 与引用）和产物。失败或未执行的标准不能提交最终验收。单人交付明确标示自验。用户退回交付后回到方案阶段并清除实施授权，修订方案需重新批准，任务群继续复用。

派发失败显示在「需要你」，发送结果不确定时不盲目重复。第三阶段继续实现队列与恢复，见下文。

验收 bench 为 .dsh-test-project-board-workflow，模拟项目位于独立 .board-test-projects 子目录。mock Bot 通过真实 DSH 文件工具写入并复核小模块；验证脚本另外导入模块执行隔离和空列表断言。静态审查与命令测试在证据中明确区分；不修改 DSH 沙箱设置以绕过环境限制。

## 后续关键约束

普通 Bot 的项目权限不得直接扩展成 Main Bot 全局权限。用户指定的主控及目录授权限定到这一需求；协作者由主控在提交方案前分配。项目关闭、Bot 删除、过期决策、存储失败必须产生明确结果，不能隐式换项目或丢记录。

## 主控分配团队（2026-10-20 用户修订）

创建、编辑待开始需求只选择一位主控 Bot，不展示协作者配置。主控字段使用 Bot 行，复用动态头像，显示名称、角色与已配置模型；点击后通过可搜索名称/角色的列表切换，支持键盘、手机布局和现有减少动画偏好。保存不派活。开始后，主控在澄清需求时读取团队角色、选择已有 Bot；工具 `assign_requirement_bots` 接收完整协作者列表与分工理由，空列表表示单人执行。用户选择的主控与项目不变，不创建或修改全局 Bot。

看板工具共九个：`read_project_board`、`create_requirement`、`assign_requirement_bots`、`plan_requirement`、`update_requirement_step`、`resume_requirement_step`、`ask_requirement_user`、`submit_requirement`、`reconcile_requirement_work`。读取工具提供团队 id、名称、角色，现有 `list_bots` 提供更完整的角色与活动信息；创建工具不再接受协作者参数。旧待开始需求编辑时保留已有分配，主控可以在开始后调整。

分配工具仅允许主控在当前需求的有效执行中调用，限澄清/设计阶段、没有待确认决策且未授权实施；已有步骤执行必须先结束。成员和任务群在同一次保存中更新，保存失败一起回退；保留成员 Session 历史，移出的 Bot 立即失去任务工具权限。分配不结束主控协调执行，也不派发协作者；主控继续提出步骤和方案。用户确认方案后沿用全局队列派发，独立验证与最终用户验收规则保持有效。卡片展示分工理由、成员和各步骤负责人。

本轮在隔离 mock bench 验证主控读取团队、分配协作者、方案审批前无实现派发、审批后执行与验收，以及重启后的成员/方案持久化。正式环境不作为测试环境。

## 项目入口与界面复用（2026-10-20 用户修订）

项目切换条旁提供「添加项目」，复用现有 FolderMenu 文件夹选择器、Card/Row 表单，以及插件的 bt-soft、bt-round、bt-input 控件样式。项目选项水平滚动，添加入口保持可见；搜索使用单层输入边框，顶部操作使用插件一致的尺寸、圆角和间距。

添加项目选择主机上已有文件夹，可选名称默认取目录名。用户接口 board-project-add 经过既有 cleanWorkDir 检查，拒绝不存在的目录、相对路径以及 DSH 数据目录；规范化后通过公开 workspaceRegistry.resolveByPath/create 注册或返回已有工作区。重复添加不新建第二个项目，不改变 Bot 或任务群的工作目录，不创建会话或启动工作。添加后选中新项目；不新增 Agent 工具，看板工具数仍为九个。

验收条件：卡片能说明现在处于哪个阶段、谁在负责、在等什么、交付了什么、证据来自哪里；单靠模型自述或一个回合结束不足以改变业务完成状态。

## 详情可读性（2026-10-20 用户修订）

需求详情优先显示待处理决策、阻塞与运行状态，随后展示执行步骤、逐项验证结果和交付物。步骤包含顺序、负责人、状态与结果预览；范围和原始执行证据可展开。验证结果明确区分通过、失败、未执行，证据来源保留完整引用。长结果只截取原文预览，不推断或生成新的结论；展开使用现有 Markdown 组件，保留完整内容。

已确认结束的 completed/killed/confirmed-stopped 后台任务合并到可展开的技术历史中，恢复记录、活动、旧验收及决策记录同样按需查看。running/stopping/failed/unknown 和未知新状态保持可见；重启后的停止核对入口不折叠，不改变恢复授权规则。所有记录保留，不修改现有看板持久数据及 Agent 工具。

手机抽屉约束嵌套 flex 宽度，长路径、哈希、代码与引用允许换行；表格仅在自身区域滚动。头部关闭和底部操作保持可见。隔离 bench 使用明确标注的合成长文本，验证 320/390 像素手机及桌面、深浅主题和展开后的宽度。

## 按需求跳过开发阶段（2026-10-20 用户修订）

五个阶段分别展示未开始、进行中、已完成、已跳过；暂停时保留已完成与已跳过的事实。不能根据阶段顺序或需求最终完成状态给前面的阶段补打钩。旧卡片未记录的阶段保持未开始；执行阶段只有非空步骤及完成证据才能证明已完成。实际提交并获批的方案可以证明设计完成，显式跳过设计时仍保留跳过状态。

继续使用九个 Agent 工具，在 `plan_requirement` 中新增可选 `stages` 数组，每项为 `{stage, status, reason}`。主控 Bot 可以把任一不适用的阶段标为 skipped 并提供具体理由，也可以给已完成的需求确认、澄清、设计阶段记录完成依据。代码实现与验证阶段只能随实际步骤及证据完成，不能用方案声明直接标记完成。阶段结果、理由、操作者与时间持久化，点击阶段可查理由。

跳过实现或验证阶段时，不为它创建占位步骤；仍适用的阶段至少包含一个步骤。两个执行阶段都不适用时可以提交零步骤方案，用户授权后只召回主控汇总已有交付物与证据。跳过不是降低验收标准：失败或未执行的验收项仍不能提交最终验收。启动、执行授权、最终用户验收继续生效，跳过设计也需用户确认执行范围。

阶段选择限主控在提交方案时决定，沿用版本检查、任务会话权限与审批。已经开始执行后不能直接跳过正在做的工作；需重新审查修订方案。退回后清除未来阶段的旧结果，历史交付和方案决策各自保留阶段快照，新方案必须重新说明跳过的执行阶段。

隔离 bench 使用真实注册工具提交仅验证的方案，确认审批前不派发、跳过状态跨服务重启保留、只读工具核对已有文件、最终用户验收后仍只对实际完成阶段打钩。单测覆盖只实现、只验证、零执行步骤、无理由或矛盾状态、越权、旧卡片和退回修订。

## 第三阶段：队列、控制和恢复

每次派发有持久 id、全局序号、方案版本和运行代次。先保存 Bot 执行占用及消息 id，再向 DSH 发送消息；收件箱尚未消费的消息也占用名额。同一 Bot 跨项目只执行一项看板工作。项目按工作区路径保留实现名额，多个方案可以先批准、随后排队；不同项目和不同 Bot 的可执行工作可并行，避免一个等待项阻塞整个队列。已完成的历史派发不参与周期性核对。

全局队列显示需求、步骤、Bot、队列位置，以及等待 Bot、当前对话或项目需求的原因。需求详情显示自身队列。重要失败和待决策事项进入「需要你」及现有徽标；普通排队、进度和成功恢复只更新界面与活动记录，不产生反复提醒。

用户控制接口为 board-pause、board-resume、board-cancel，携带唯一 requestId 防止重复点击或重试重复执行。暂停/取消先持久保存 pausing/cancelling 状态并增加运行代次，立即阻止旧执行继续修改状态或发起新修改工具；撤下任务会话收件箱消息并调用 DSH 的取消接口。确认 Agent 空闲、没有会话切换在进行后，才转为 paused/cancelled 并释放占用。暂停不是操作回滚；已经完成的文件修改和外部效果保留。

暂停后继续保留已完成步骤，未完成工作以新的执行记录重新排队，并核对已发生的效果。用户继续时回到队列末尾；自动重启接续保留原执行的排队优先级。取消保留步骤、产物、证据、决策和操作历史，清除待处理决策；默认隐藏，勾选「显示已取消」后在待开始列显示明确的「已取消」标记，不混入用户验收的已完成列。

启动时逐项查询 DSH 的公开 Session 历史及持久收件箱。已在收件箱或仍在运行的消息直接接管，不重复发送；明确未送达才沿用原消息 id 发送。已有步骤完成回执直接结束派发，不再执行；收到消息后中断的任务创建一次接续记录并关联原 id。旧的通用 resume 逻辑跳过看板任务，避免两套机制同时恢复。

恢复 Bot 先只能读取，必须通过 reconcile_requirement_work 提交观察到的进展与文件/会话引用，才能继续修改；无法确认时可报告阻塞。完成回执与业务变更在同一次状态保存中落盘，避免写了“完成”却丢了执行回执。读取会话失败时保留占用、显示待处理并稍后重查，不推测消息是否送达。连续三次自动接续仍被中断会停止自动恢复，交由用户检查后重试。

DSH 的 generation 结束事件不代表工具或 Agent 已空闲，因此执行名额不会在单个 turn/end 上立即释放。兼容公开日志中的 interrupted，以及正常关闭时的 aborted/disposed。旧代次、旧执行和旧会话的回调不能更新新执行；只读团队实例也不能取得执行权限。

第三阶段 bench 使用 .dsh-test-project-board-queue、3110/8810 端口和受环境检查保护的只读会话审计插件。故障测试在确认进程组 PID 和 DSH_HOME 均属于该 bench 后才发 SIGKILL。验证暂停、取消、持久排队、恢复核对、原消息计数、实际文件写入计数，以及暂停/取消状态跨重启保留。测试模型使用真实文件工具，未放宽 shell 沙箱限制；不声称外部副作用具有通用的 exactly-once 保证。

## 第四阶段：shell 后台任务的停止与核对

看板通过 DSH 公开 `ctx.jobs` 接口观察任务、按所属 Session 请求停止，并等待 `killed/completed` 终态。failed 记录可能来自生产者停止时抛错，不能证明进程已停止，因此也需核对。Agent 空闲、回合结束或 shell 超时转到后台都不释放执行名额；任务仍运行时不能提交步骤完成或交付验收。只处理该需求任务会话拥有的任务，不停止无 owner 或其他会话的任务。详情展示后台任务状态，保存启动时间、所属执行、状态及用户核对依据，不复制可能含敏感信息的 shell 命令或输出。

暂停是停止进程并保留已有文件，继续时创建接续执行并先核对保存的进度，不使用操作系统 SIGSTOP/SIGCONT 保留活进程。取消同样等待进程停止，保留产物与历史；停止失败会继续占用名额并显示问题，不能假称已暂停或已取消。

DSH 0.2.0-rc.2 的 JobRegistry 只在当前进程中存在。主机进程崩溃后，旧的 running/stopping 记录标记为 unknown，保留 Bot/项目占用且禁止自动重跑。任务 id 可能在新进程复用，因此不能用旧 id 去杀新进程的任务。注册事件持久化前发生崩溃时，Session 中未核实的 shell 调用也会阻止自动接续。

用户核对实际进程及已有副作用后，可以在详情的“核对后台任务是否停止”入口记录依据。`board-background-resolve` 只供用户 API 使用，不提供 Bot 工具；校验所确认的任务集合未变化，并先保存依据，再允许恢复。明确标记为“用户已核实停止”，不冒称 DSH 确认。仍在 pausing/cancelling 的需求只继续完成停止流程，不擅自变回 active。恢复 Bot 仍须执行 reconcile_requirement_work，且保留原始启动记录及已有文件；不能把核对动作当作工作完成。

本轮 bench 使用 `.dsh-test-project-board-shell`、3112/8812。通过系统发行版的 bubblewrap RPM 解压到专用缓存，仅给 bench PATH 使用，没有关闭沙箱、修改 DSH 或更改生产服务。mock 模型通过真实 DSH bash 工具运行持续写心跳的进程；包含显式后台运行、前台超时自动转后台、Agent 空闲后的暂停/取消、保留输出、暂停后重启及接续、硬崩溃后保持未知、按进程 argv 与独立 DSH_HOME 核实停止后接续。另一个 Bot 通过真实前台 shell 断言原始启动次数为 1，用户最终验收才完成需求。

边界：停止仅覆盖 DSH 注册并管理的任务，不承诺回滚外部副作用，也不承诺控制脱离 DSH 的守护进程或外部服务。任务提示要求不使用 nohup/disown/外部 supervisor 脱离管理。硬崩溃后状态无法从 DSH 公共接口证实时，需要用户核对；不会根据注册表为空推断进程已经停止。
