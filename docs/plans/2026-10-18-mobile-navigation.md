# 窄屏导航

- 日期：2026-10-18
- 状态：草稿，待维护者定；定下来之后本文改成「已定的行为」的写法
- 相关：#315（移动端可用性）；本改动属于行为变更，需要单独的上游 issue，编号待补

## 为什么

DS Bot 的界面在窄屏上不可用：左侧 Bot 侧栏常驻，和聊天列并排挤在 360–430px 里，聊天列只剩几十像素；右侧详情面板打开后又把剩下的宽度吃掉。这一轮（#315）已经把「挤死」的部分修掉了——详情面板在窄屏改成覆盖聊天、设置页在窄屏改成整页——但侧栏常驻本身没有解决：手机上仍然是一屏两栏。

要的是常见聊天应用那种两级导航：**先是一个 Bot 与群聊的列表页，点进去才是那个 Bot / 群聊的聊天界面，返回回到列表。** 这里只借「两级导航」这个模式，视觉不借：列表用的还是现有的头像、名称、预览、未读标记和配色。

取舍：

- **桌面端必须保持常驻侧栏**，不能回归。窄屏的两级导航是一条只在窄屏生效的规则，不是把侧栏改成列表。
- **只作用于 Bot 面。** DSH 自己的 Agent 会话面（插件把界面让出去的那种）保持原样，插件不替 DSH 决定导航。
- 列表页不新造数据：用侧栏已经在渲染的那套（头像状态、名称、角色、最后一条、未读、置顶），顺序也用同一个排序，避免两个视图给出不同的列表。

## 如何判定是不是移动端

要的是「识别移动端浏览器再应用这套 UI」，不是无条件按窗口宽度切。判定式由三件事组成，CSS 和 JS 用同一个来源：

1. **能力**：`(hover:none) and (pointer:coarse)`。这是「触屏设备」的准确表达——没有可悬停的主指针、主指针是粗的。仓库里已经在用这个路子（5 处 `@media (hover:none)`），只是没覆盖全。
2. **宽度**：`(max-width:640px)`。两级导航本身需要窄屏才成立，光有触屏不够——平板横屏是触屏，但 1024px 放得下两栏，不该切成列表页。
3. **排除桌面应用**：`<html>` 上没有 `data-platform`。

完整判定：`(hover:none) and (pointer:coarse) and (max-width:640px)`，且不是桌面应用。

### 为什么用 `data-platform` 排除桌面，而不是 UA

DSH 自己就给了这个标记。它判断运行环境的方式是（`@deepseek-ai/dsh-client-shortcuts` 的 `detectEnvironment`）：

> `document.documentElement.dataset.platform` —— 由 Electron preload 在桌面应用里打上；有它就是桌面运行时，没有就是 web。

也就是说 `<html data-platform>` 存在 ⟺ 跑在 DSH Desktop 里。插件已经在用这个属性（`styles.js:541` 的 `html[data-platform=darwin]`）。它是布尔事实，不会漂移也不会被伪装。

因此**连 UA 兜底都不需要**：`navigator.userAgent` 继续只出现在诊断信息里（`diagnostics.js:46`），不参与判定。UA 会漂移、会被伪装，而且我们要的两个事实（触屏能力、运行环境）都有更好的来源。

CSS 侧这样写（媒体查询里没法测属性，所以排除条件放在选择器上）：

```css
@media (hover:none) and (pointer:coarse) and (max-width:640px){
  html:not([data-platform]) .bt-mobile-nav{ /* … */ }
}
```

JS 侧同一件事：`matchMedia(同一个查询字符串).matches && window.dshDesktop === undefined`。两个标记出自同一个事实（Electron preload），不会互相打架。插件里已经有 `window.dshDesktop` 的用法（`diagnostics.js:44`、`feedback.js:48`）。

### 怎么保证 CSS 和 JS 不脱节

判定字符串只写一份，放在一个新模块里（例如 `src/client/media.js`），两边都从它取：

```js
export const TOUCH = '(hover:none) and (pointer:coarse)'
export const NARROW = '(max-width:640px)'
export const MOBILE_NAV = `${TOUCH} and ${NARROW}`
```

CSS 把它插进模板字符串（`styles.js` 本来就往里插 `${SPRING_SHAPE.duration}` 这类值，是现成写法）；JS 用它建一个 source，和现有的 `createSource`（`sources.js:4`）一样，组件用同一套 `useXxx` 读。

### 跟随变化，不是只在初始化读一次

用 `matchMedia(...)` 的 `change` 事件驱动那个 source：旋转屏幕、缩放窗口、给 iPad 接上触控板（`pointer` 会从 `coarse` 变 `fine`）都要能跟着切，不能只在启动时读一次。桌面标记是文档级的，装好就不变。

### 和 P1 已有的宽度断点不是一回事

本 PR 的 P1 用的是纯 `(max-width:640px)`（设置页导航条、用量页、记忆弹窗）。那是「内容在窄区域里怎么排」——桌面窗口拖窄同样该生效，和是不是移动端无关。这里的判定管的是「导航结构用哪一套」，是设备形态问题。两个判定并存是故意的，不是漏改。

## 方案与取舍

以下每条都给可选做法、代价，以及倾向。倾向只是建议，不是结论。

### 一、断点怎么定

**A. 视口宽度断点，取 640px。**

- 理由：和本 PR 已经加进窄屏样式的那个断点一致，一处生效；阈值可测、可预期。
- 代价：桌面用户把窗口拖到 640px 以下会切成两级导航（不是回归，是换一种形态）；平板竖屏（768px）仍是常驻侧栏。

**B. 跟随 shell 的侧栏展开/收起状态（slot 的 `wide`）。**

- 理由：`sidebar.workspaces` 的 slot props 里已经有 `wide`，还有一个 `expandSidebar` 回调（`@deepseek-ai/dsh-client-ui-sidebar`）。复用它就不需要自己判宽度，用户在桌面上手动收起侧栏也走同一套。
- 代价：桌面收起侧栏现在是一个 56px 的 rail（插件里是 `.bt-rail`），把它变成整页列表会改掉桌面已有的行为，属于回归风险；rail 的宽度和动画归 shell 管，插件要盖掉它。

**C. 断点 + 设置里的开关。**

- 理由：给不愿意换的人一条退路。
- 代价：多一个设置项、多一组要测的状态，收益不明显。

**倾向 A。** 桌面常驻侧栏是红线，A 用一个明确阈值保住它；B 会连带改掉桌面已经存在的收起行为。

### 二、列表页放什么

内容沿用侧栏现有的那一套，不新增信息：头像（带运行中 / 等待回答 / 等待审批的状态）、名称、角色标签、最后一条预览、时间、未读点、置顶标记；Main Bot 置顶；顶部保留搜索、新建、更新检查这几个入口。

**A. 与侧栏同一个列表，只是变成整页宽。**

- 理由：顺序、置顶、隐藏项规则完全一致，两个视图不可能给出不同结果（同一个 `order`）。
- 代价：整页宽之后每行的信息显得稀疏，可以考虑把时间和预览都显示出来。

**B. 分成「Bot」「群聊」两段。**

- 理由：一屏里两类目标更清楚。
- 代价：和现有的按最近活动排序冲突（现在是 Bot、群聊、Agent 混在一起按时间排）；两段各占一个标题行。

**C. 顶部 tab 切 Bot / 群聊 / Agent。**

- 理由：目标多时找得快。
- 代价：多一层交互，和「列表 → 会话」的两级结构叠成三层。

**倾向 A**，另外补一个时间戳。侧栏的行现在只有预览没有时间；相对时间的写法 `AgentSessionRow` 里已经有了，`useSessions` 里也有 `updatedAt`（现在的排序就在用它），所以不用新数据。

### 三、进入会话后顶部是什么

**A. 在插件自己的浮动胶囊（`.bt-head`）左边加返回箭头，胶囊继续显示当前 Bot / 群聊名。**

- 理由：`.bt-head` 已经是插件自己的 DOM，视觉和点击都在插件手里；胶囊本来就显示当前名字，不需要再写一遍。
- 代价：窄屏上左边多一个 32–40px 的按钮，胶囊的可用宽度要重新算。

**B. 占用 DSH header 的 leading 位。**

- 理由：那里本来就是 shell 放返回/侧栏开关的地方，插件现在也把 `[class*="_headerLeading"]` 绝对定位到了左边。
- 代价：依赖 shell 的内部结构，插件已经为这个位置写过 `!important` 的定位规则，再加一层更脆。

**C. 单独一条返回栏，不和胶囊同层。**

- 理由：返回和「当前在哪」分开，逻辑更直白。
- 代价：多占一行高度，手机上不划算。

**倾向 A。** 右侧的边栏开关（`.bt-head-side`）保持原位；窄屏下点胶囊仍然打开详情面板（见下一条）。

### 四、窄屏下右侧详情面板怎么放

**A. 全屏覆盖。** 本 PR 的 A1 已经是这个行为：视口窄于「聊天列最小宽 + 面板最小宽」时，面板铺满视口、不再给聊天列让位。

- 理由：已经在 390×844 / 360×800 下出过图。
- 代价：它现在是独立的一层，返回语义没有和列表页统一。

**B. 第三层：列表 → 会话 → 详情，每层整页，返回一层层退。**

- 理由：和两级导航合成一条返回栈，用户按返回的顺序可预期；A 的几何可以直接用。
- 代价：要多一个「当前在第几层」的状态，横竖屏切换时要能退回常驻侧栏而不丢当前会话。

**C. 底部半屏抽屉。**

- 理由：会话内容还能露出一半，和键盘共存的习惯也成熟。
- 代价：和输入法抢空间；面板里的浏览器视图本来就适合整页。

**倾向 B，几何沿用 A。** 详情层打开时，返回箭头先关详情、再回列表；两层都保留 Escape。

## 倾向的方案（合起来）

窄屏（≤640px）下：隐藏 shell 的侧栏列，Bot 面渲染一个整页列表（内容与顺序同侧栏，另加时间）；点一行进入会话，顶部胶囊左侧出现返回箭头；点胶囊打开详情，详情是同一返回栈的第三层。视口变宽时自动退回常驻侧栏，当前会话不变。桌面端的行为一行不改。

## 不做什么

- 不做底部 tab 栏（Bot / 群聊 / 设置三格）。那解决的是另一件事，也不是这个 PR 的范围。
- 不改桌面端的侧栏布局、收起行为和 rail。
- 不替 DSH 决定 Agent 会话面的导航。
- 不引入路由库；不为了「返回」去接管浏览器的历史。
- 不借任何其他产品的视觉素材（仓库硬规则：只用原创素材）。

## 已知限制

- **浏览器和系统的返回手势管不了。** 我核过 DSH 的客户端包，没有一处用 `history` / `pushState` / `popstate`，会话不在 URL 里，所以系统返回会离开页面而不是回列表。返回只能是应用内控件。要不要插件自己压一层历史，需要维护者定。
- **窄屏下 shell 的侧栏列被隐藏**，其它挂在侧栏上的 DSH 插件（文件、终端等）在窄屏的 Bot 面里也就看不到了。是否可接受需要维护者定。
- 首次加载落点：窄屏下默认进列表还是上次的会话，需要一起定。倾向进列表（符合两级导航），代价是刷新后不记得上次在哪。
- 横竖屏切换：390 → 844 要能无损退回常驻侧栏，且当前会话不丢。
- 键盘弹起时的高度变化依赖 `dvh`，这部分已在本 PR 里做过。
